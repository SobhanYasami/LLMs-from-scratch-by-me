Aim. Build a feeling for max_length, stride and batches using tiny numbers instead of token IDs.

Pretend the "text" is the numbers 0 to 11. Each row is one (input, target) window; the target is the input moved one step to the right.

stride 1: heavy overlap

max_length = 4, stride = 1
input [0 1 2 3]   target [1 2 3 4]
input [1 2 3 4]   target [2 3 4 5]
input [2 3 4 5]   target [3 4 5 6]
...
input [7 8 9 10]  target [8 9 10 11]    -> 8 windows

stride 4: no overlap, nothing skipped

max_length = 4, stride = 4
input [0 1 2 3]   target [1 2 3 4]
input [4 5 6 7]   target [5 6 7 8]
                                       -> 2 windows  (the third would need target[12])

The last window is dropped because its target would run off the end. That is why the loop stops at len - max_length.

How many windows?

With n tokens: ceil((n - max_length) / stride). For the story, n = 5,145: stride 4 gives 1,286 windows; stride 1 would give 5,141.

Batches

batch_size = 2, drop_last = true, 5 windows w0..w4
batch 0: w0 w1
batch 1: w2 w3
(w4 dropped: a batch of 1 would be a different size)

with shuffle = true the window order is mixed first:  w3 w0 w4 w1 w2 ...

Which settings when?

SettingSmall valueLarge value
max_lengthcheap, little contextmore context per example, more memory
stridemany overlapping examples, risk of overfittingfewer examples, no repetition
batch_sizeless memory, noisier updatessmoother updates, more memory

Try it

  1. Predict the window count for n = 20, max_length = 5, stride = 3, then verify with your code.
  2. Run the same loader with shuffle=true twice with the same seed, then with different seeds. What changes?
Answer to 1ceil((20 - 5) / 3) = 5 windows, starting at 0, 3, 6, 9, 12.
